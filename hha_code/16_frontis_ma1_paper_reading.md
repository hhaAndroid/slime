# Frontis-MA1 / OpenMLE 论文通俗解读

> 论文：[Frontis-MA1: Training an AI4AI Model towards Recursive Self-Improvement in Machine Learning Engineering](https://arxiv.org/pdf/2607.28568)
>
> 本文不介绍评测分数，重点回答三个问题：整个系统到底怎么运转、训练阶段为什么需要搜索树、论文所说的“自进化”到底是什么。

## 1. 先说最容易误解的地方

这篇论文不是下面这个过程：

```text
给模型一个任务
-> 模型自己调用 slime 训练一个新大模型
-> 再用新大模型解决任务
```

真实过程是：

```text
论文作者准备大量机器学习任务
        │
        ▼
大语言模型生成解决任务的 Python 程序
        │
        ▼
在 sandbox 中执行 Python 程序
        │
        ▼
得到程序分数、错误日志和运行时间
        │
        ▼
把这些真实执行结果变成 SFT 数据或 RL reward
        │
        ▼
论文作者使用 slime 更新大语言模型参数
        │
        ▼
得到更会写和修改机器学习程序的 Frontis-MA1
```

这里存在两种完全不同的“训练”：

1. **训练大语言模型**：论文作者使用 slime，把基础 Qwen 模型训练成 Frontis-MA1。
2. **训练任务模型**：Frontis-MA1 生成的 Python 程序在 sandbox 中训练 LightGBM、XGBoost、神经网络等具体任务模型。

第二种训练只是为了检查候选程序好不好，它不会直接修改 Frontis-MA1 的参数。

一句话概括：

> slime 训练的是“写机器学习程序的大语言模型”；候选 Python 程序训练的是“解决某一个数据集任务的小模型”。

## 2. 先认识系统里的五个角色

为了不被 OpenMLE-Gym、ERL、Evo 等名字绕晕，可以先把整个系统看成一个软件项目团队。

| 角色 | 可以类比成 | 实际职责 |
|---|---|---|
| 基础模型 / Frontis-MA1 | 程序员 | 根据任务、旧代码和反馈，生成一份新的完整 Python 程序 |
| 搜索器 | 项目经理 | 决定下一步写新方案、改旧方案、修 bug，还是合并两个方案 |
| OpenMLE-Gym / sandbox | 运行和验收环境 | 真正运行程序，检查输出，返回分数、报错和运行时间 |
| slime | 大模型训练系统 | 根据 SFT 数据或 RL reward 更新语言模型参数 |
| 任务模型 | 程序员写出的产品 | 由候选 Python 程序训练出来，例如一个房价预测模型 |

需要一直记住：

- 搜索器是人预先写好的程序，不是 Frontis-MA1 自己发明的。
- slime 只在训练 Frontis-MA1 时使用。
- sandbox 只负责执行和评价候选程序。
- Frontis-MA1 负责生成代码，但不负责更新自己的参数。

## 3. 整个流程分成哪些阶段

论文中的训练和测试不是同时发生的，可以按时间分成五个阶段：

```text
阶段 0：准备大量可执行任务

阶段 1：离线采集 SFT 数据
        ├── 独立生成完整方案
        └── 用搜索树收集修改、修错和合并方案的数据

阶段 2：使用 slime 做 SFT

阶段 3：使用 sandbox reward 做在线 RL

阶段 4：冻结 Frontis-MA1，用 OpenMLE-Evo 解决新任务
```

下面用一个“房价预测”任务贯穿整个流程。

## 4. 阶段 0：先准备可以自动验收的任务

假设有一个任务：

> 根据房屋面积、位置、房龄等信息预测房价，最终生成 `submission.csv`，评价指标是 RMSE。

OpenMLE-Gym 会把它整理成一个标准任务包，其中包括：

- 给模型看的任务描述；
- 公开的训练数据；
- 公开的测试输入；
- 一个 `sample_submission.csv`；
- 对模型隐藏的测试答案；
- 计算 RMSE 的评测程序；
- 最长运行时间、CPU/GPU 等资源限制。

以后无论谁生成一份候选 Python 程序，Gym 都能自动完成：

```text
启动隔离环境
-> 运行候选程序
-> 检查是否生成 submission.csv
-> 检查行数、列名、顺序和数值是否合法
-> 使用隐藏答案计算分数
-> 返回执行结果
```

返回结果不只有一个分数，还会区分：

- 程序正常运行并成功提交；
- Python 运行报错；
- 程序内容为空；
- 运行结束但没有生成 submission；
- submission 格式错误，无法评分；
- 运行超时。

这一步解决的是一个基础问题：

> 怎样自动判断一份机器学习代码是真的有效，还是只看起来像正确答案？

## 5. 阶段 1A：独立生成 Draft，收集完整答案

有了大量可执行任务之后，作者首先让 teacher model 为每个任务生成多份独立程序。

以房价预测为例：

```text
房价预测任务
├── Draft 1：RandomForest
├── Draft 2：LightGBM
├── Draft 3：简单神经网络
└── Draft 4：CatBoost
```

这里每个 Draft 都是一份完整 Python 程序，不是几句建议。

每份程序都被送进 sandbox：

```text
Draft 1 -> 能运行，得到一个分数
Draft 2 -> 能运行，得到另一个分数
Draft 3 -> 训练超时
Draft 4 -> submission 格式错误
```

然后系统做过滤：

- 删除运行失败的程序；
- 删除结果重复或高度重复的程序；
- 在同一个任务内比较有效程序；
- 只保留质量较好的少量程序。

最终得到一批最普通的 SFT 数据：

```text
输入：房价预测任务描述
输出：一份真实运行过、质量较好的完整 Python 程序
```

这条路径主要教基础模型：

> 面对一个新任务，怎样从零写出一份完整的机器学习方案。

论文把这种从零生成称为 `Draft`。

但只有 Draft 数据还不够，因为测试时系统希望模型能根据实验结果不断改代码。

## 6. 阶段 1B：为什么需要搜索树

### 6.1 只有 Draft 数据会缺少什么

如果训练数据全部是：

```text
任务描述 -> 最终优秀程序
```

模型只能学习“一个好答案大概长什么样”。它没有学习下面这些能力：

- 已经有一份程序时，怎样继续改进；
- 程序报错时，怎样根据 traceback 修复；
- 两个不同方案各有优点时，怎样组合它们；
- 一次修改到底有没有比父程序更好。

因此作者还需要下面三种数据：

```text
旧程序 + 执行结果 -> 更好的程序        Improve
失败程序 + traceback -> 修复后的程序    Debug
两个父程序 + 各自结果 -> 融合程序       Crossover
```

搜索树就是用来生产和保存这些“程序修改过程”的。

### 6.2 搜索树是模型自己生成的吗

不是。

搜索树由人提前写好的搜索器管理。在 SFT 数据采集阶段，论文使用 AIRA-Evo 风格的 controller。

controller 负责：

- 选择下一次操作；
- 从已经执行过的程序中选择父节点；
- 把任务、父程序和执行反馈放进 prompt；
- 调用 teacher model 生成新程序；
- 把新程序交给 sandbox；
- 保存新程序、分数、错误和父子关系。

模型只负责根据 controller 给出的输入生成代码。

可以简化成：

```text
搜索器决定“接下来做什么、改哪份代码”
模型负责“具体写出新代码”
sandbox 负责“运行和验收新代码”
```

### 6.3 一棵搜索树是怎么长出来的

继续使用房价预测例子。

#### 第一步：生成根节点

搜索器先调用 Draft：

```text
operator = Draft
task = 房价预测
```

teacher model 生成程序 A：

```text
A：RandomForest + 基础数据清洗
```

sandbox 执行 A，并保存：

```text
程序代码
执行状态
验证分数
运行时间
日志
```

#### 第二步：从 A 做一次 Improve

搜索器把下面的信息交给 teacher model：

```text
operator = Improve
task = 房价预测
parent = 程序 A
feedback = A 的分数和运行日志
```

teacher model 生成程序 B：

```text
B：LightGBM + 新的类别特征处理
```

sandbox 执行 B。如果 B 比 A 更好，就得到一条有价值的 Improve 数据：

```text
输入：任务 + A 的代码 + A 的执行反馈
输出：B 的代码
```

树变成：

```text
A：RandomForest
└── B：LightGBM + 类别特征
```

#### 第三步：从 A 再尝试另一条路线

搜索器不一定只能继续修改 B，它可以重新回到 A，再尝试另一个方向：

```text
A：RandomForest
├── B：LightGBM + 类别特征
└── C：CatBoost + 交叉验证
```

这就是使用“树”而不是单链的原因。

如果只有一条链：

```text
A -> B -> C -> D
```

某一步走错以后，后续程序可能一直在错误方向上修补。树可以保留所有历史版本，让搜索器回到旧的好节点尝试新方向。

#### 第四步：收集 Debug 数据

假设 C 运行失败：

```text
C：CatBoost + 交叉验证
错误：类别特征的数据类型不符合要求
```

搜索器调用 Debug：

```text
operator = Debug
parent = C
feedback = C 的 traceback
```

teacher model 生成修复后的 D：

```text
A
├── B
└── C：运行失败
    └── D：修复类别特征类型
```

如果 D 能正常运行，就得到 Debug 训练数据：

```text
输入：C 的失败代码 + C 的 traceback
输出：D 的修复代码
```

#### 第五步：收集 Crossover 数据

现在 B 和 D 是两条不同路线：

```text
B：LightGBM 的数值特征比较好
D：CatBoost 的类别特征处理比较好
```

搜索器可以选择 B 和 D，调用 Crossover：

```text
operator = Crossover
parent 1 = B
parent 2 = D
```

teacher model 生成程序 E：

```text
A
├── B ──────────┐
└── C -> D ─────┴── E：融合两个分支的方案
```

严格来说，Crossover 节点有两个父节点，因此整个结构更接近有向图。论文和本文仍使用更直观的“搜索树”说法。

### 6.4 搜索树为什么必须保存父子关系

如果系统只保存所有程序和最终分数，不保存树结构，就无法回答：

```text
B 是从哪个程序改出来的？
B 是否真的比自己的父程序更好？
D 修复的是哪个错误？
E 使用了哪两个父程序？
某个早期修改是否被最终程序保留？
```

保存父子关系有五个直接用途。

#### 用途一：判断 Improve 是否有效

只有比较 child 和它自己的 parent，才能知道这次修改是否真正带来进步。

#### 用途二：生成 Debug 训练样本

必须知道哪份失败代码和哪条 traceback 对应哪份修复代码。

#### 用途三：检查 Crossover

需要知道 child 是否比两个 parent 都更好，以及是否真的继承了两条分支的有效部分。

#### 用途四：保留多种尝试

搜索器可以从同一个父程序尝试多个方向，而不必让最新修改覆盖所有旧版本。

#### 用途五：让训练方式和测试方式一致

测试时 OpenMLE-Evo 也会面对已有程序、失败程序和多个分支。训练时提前构造这些状态，模型才真正学过 Improve、Debug 和 Crossover。

### 6.5 搜索树中的节点不会全部拿去训练

搜索树只是原始数据，里面会有大量没用甚至有害的尝试。

例如：

```text
A：提出一个合理方案，但程序有 bug
└── B：修复第一个 bug，仍不能运行
    └── C：修复第二个 bug，终于可以运行
        └── D：进一步改进，效果更好
```

不能简单把 A、B、C、D 全部当作正确答案。数据筛选器还要判断：

- A 的整体方案是否被最终程序保留；
- B 的修改是否真的被 C 和 D 继承；
- C 是否真正解决了对应错误；
- D 是否确实优于 C；
- 某一步是否只是盲目重试；
- 是否只是缩小数据量来逃避超时；
- 是否偷偷下载外部资源或修改环境；
- 是否利用 evaluator 漏洞刷分。

只有对最终有效程序有实际贡献的步骤才进入 SFT 数据。

所以搜索树的真正作用不是把搜索过程原样教给模型，而是：

> 先制造大量真实的程序修改过程，再从中挑出有价值的局部修改作为监督数据。

## 7. 阶段 2：收集好数据后，才使用 slime 做 SFT

经过前面的两条路径，作者得到四类训练样本。

### Draft 样本

```text
输入：任务描述
输出：一份完整、可执行的程序
```

### Improve 样本

```text
输入：任务描述 + 一个父程序 + 父程序执行反馈
输出：一份真正更好的完整程序
```

### Debug 样本

```text
输入：任务描述 + 失败程序 + traceback
输出：修复后的完整程序
```

### Crossover 样本

```text
输入：任务描述 + 两个父程序 + 各自执行反馈
输出：融合两个方案有效部分的完整程序
```

这些数据会被整理成普通的对话训练格式：

```text
system message
user message
assistant answer
```

随后作者使用 slime 对基础 Qwen 模型进行全参数 SFT：

```text
基础 Qwen 模型
        +
四类经过执行验证的 SFT 数据
        │
        ▼
slime 进行参数更新
        │
        ▼
SFT checkpoint
```

这一阶段是标准的离线监督训练。训练数据已经提前保存好，通常不需要在每个 gradient step 重新运行 sandbox。

## 8. 阶段 3：SFT 之后再做在线 RL

SFT 教模型模仿经过筛选的好例子，但还不等于模型自己生成时一定稳定。因此论文继续做 RL。

### 8.1 RL 是 rollout 和训练交替发生

在线 RL 的外层循环是：

```text
第 1 轮：
当前模型生成一批程序
-> sandbox 执行
-> 得到 reward
-> slime 更新模型参数

第 2 轮：
更新后的模型再生成一批程序
-> sandbox 执行
-> 得到 reward
-> slime 再更新

第 3 轮：
继续重复
```

因此，“生成、执行、保存结果、更新模型”不断交替发生的是 RL 阶段。

SFT 数据采集则不同：它先离线收集和过滤大量数据，然后集中训练。

### 8.2 一轮 RL rollout 里面发生什么

假设当前训练 Improve。

系统先准备同一份输入：

```text
任务描述
operator = Improve
一个已经执行过的父程序
父程序的反馈
```

当前模型针对这个输入生成多个候选：

```text
候选 1 -> sandbox -> reward 1
候选 2 -> sandbox -> reward 2
候选 3 -> sandbox -> reward 3
候选 4 -> sandbox -> 运行失败
```

系统比较这组候选，更强的程序获得更积极的学习信号，失败或明显较差的程序获得较弱或负面的学习信号。

然后 slime 使用这些 reward 更新大语言模型参数，使模型以后更可能生成高质量程序。

### 8.3 为什么不同任务的分数不能直接使用

不同任务的指标可能完全不同：

```text
分类任务：accuracy 越大越好
回归任务：RMSE 越小越好
排序任务：可能使用另一种范围的指标
```

因此系统会先把不同任务的分数转换成统一方向，并关注同一任务、同一输入下候选之间的相对好坏。

不用记论文中的公式，只需要理解：

> RL 不会拿房价任务的 RMSE 和图像任务的 accuracy 直接比较，而是先判断每个候选在自己的任务和采样组里表现如何。

### 8.4 RL 里为什么还会出现程序数据库和搜索关系

训练 Draft 不需要父程序：

```text
任务 -> 多个 Draft -> 执行 -> reward
```

但另外三个操作都必须先有合适的训练状态：

- Improve 需要一个有效父程序；
- Debug 需要一个失败父程序及错误信息；
- Crossover 需要两个不同的有效父程序。

因此 RL 过程中也会为每个任务保存一个 program database：

```text
已经生成过的程序
每个程序的执行状态
分数和错误
父子关系
被选中过多少次
从它产生的 child 表现如何
```

训练 controller 再从数据库中挑选值得练习的状态。

选择逻辑不是简单地永远选择最高分程序，也不是完全随机。它大致兼顾：

- 父程序本身是否有希望；
- 从这个父程序生成不同 child 时，结果是否还有明显差异；
- 这个父程序是否已经被反复练习很多次。

目的很直观：

> 多练有潜力、仍有学习空间的状态，同时避免永远围着同一个程序训练。

### 8.5 Draft 如何启动 database，后续操作如何接上

这里不是先在 RL 开始前建好一棵完整搜索树，再拿它训练。database 和模型训练是在 rollout 过程中同时向前推进的：

```text
生成候选程序
-> sandbox 执行
-> 把代码和执行结果写入 database
-> 从 database 选择下一轮 parent
-> 生成 child
-> sandbox 执行 child
-> 用 reward 更新模型，同时把 child 写回 database
```

一个程序不能在刚生成、还没有执行时就成为完整节点。系统至少要知道它是否能运行、reward 是多少、有什么错误，才能判断它接下来适合 Improve 还是 Debug。

#### 第 0 轮：database 为空

一个任务刚进入 RL 时，还没有任何父程序：

```text
Task Database：空
```

这时只能从不需要 parent 的 Draft 开始。当前 policy 针对同一个任务生成一组程序：

```text
Draft A
Draft B
Draft C
Draft D
```

它们分别进入 sandbox。假设结果是：

```text
A：成功，正 reward
B：成功，正 reward
C：Python 运行报错
D：没有生成 submission
```

系统把代码和执行结果一起保存，database 才有了第一批节点：

```text
Task Database
├── A：成功，正 reward
├── B：成功，正 reward
├── C：运行错误，包含 traceback
└── D：submission 缺失
```

Draft 因而承担了“启动搜索状态”的作用：

```text
成功 Draft -> 可以作为 Improve 的 parent
失败 Draft -> 可以作为 Debug 的 parent
多个成功 Draft -> 可以作为 Crossover 的两个 parent
```

#### 第 1 轮：从成功节点训练 Improve

controller 可以从成功节点中选择 A，构造 `Improve(A)`：

```text
输入：任务 + A 的代码 + A 的执行反馈

当前 policy 生成：
A1、A2、A3、A4
```

每个 child 都在 sandbox 中执行。执行结果有两个用途：

1. 比较 A1～A4，为当前 RL rollout 计算学习信号并更新 policy；
2. 把 A1～A4 连同 `parent=A`、reward 和错误写回 database。

搜索关系变成：

```text
A
├── A1
├── A2
├── A3
└── A4

B
C
D
```

#### 第 2 轮：从失败节点训练 Debug

controller 可以选择失败节点 C：

```text
输入：任务 + C 的代码 + C 的 traceback
操作：Debug(C)
输出：C1、C2、C3
```

C1～C3 执行后用于 RL 更新，也作为 C 的 child 写回 database。

#### 第 3 轮：从两个成功节点训练 Crossover

当 database 中至少有两个合适的成功节点，例如 A1 和 B，controller 才能构造：

```text
Crossover(A1, B)
```

新生成的 X1、X2 经过 sandbox 执行、参与 RL 更新，再以 A1 和 B 为两个 parent 写回 database。因为一个节点可以有两个 parent，严格来说它最终是搜索图，只是通常仍简称搜索树。

#### 后续轮次：搜索图和 policy 同时增长

完整时序可以简化为：

```text
初始：SFT checkpoint，database 为空

第 1 轮：Draft
-> 执行
-> 写入第一批成功和失败节点
-> slime 更新 policy

第 2 轮：Improve(成功节点)
-> 执行 children
-> 写回 database
-> slime 更新 policy

第 3 轮：Debug(失败节点)
-> 执行 children
-> 写回 database
-> slime 更新 policy

第 4 轮：Crossover(两个成功节点)
-> 执行 children
-> 写回 database
-> slime 更新 policy

第 5 轮以后：继续从不断扩大的 database 选择训练状态
```

这里没有循环依赖，因为 Draft 不需要 parent，先提供种子节点；Improve、Debug 和 Crossover 再利用这些节点继续扩展。

也不要求每批 Draft 后严格按 `Improve -> Debug -> Crossover` 的固定顺序执行。controller 会根据当前 database 中是否存在合格状态选择操作：

```text
没有可用 parent          -> Draft
存在成功节点             -> 可以 Improve
存在失败节点             -> 可以 Debug
存在两个合适的成功节点   -> 可以 Crossover
```

搜索树本身不参与反向传播。它只是保存“当前有哪些可训练状态”；sandbox 提供 child 的 reward，slime 才负责根据 reward 更新 policy。

### 8.6 为什么要异步执行

候选程序的运行时间差异很大：

```text
语法错误：几秒就失败
LightGBM：可能几分钟
神经网络：可能几十分钟
超时程序：一直运行到预算结束
```

如果整批数据必须等最慢程序结束，已经完成的结果和训练资源都会空等。

因此论文让不同“生成 + 执行”任务独立运行。哪一组先完成，哪一组就先交给 trainer 使用，不必等待最慢任务。

这是一项训练效率设计，不改变前面的基本逻辑。

## 9. 阶段 4：训练结束后怎样解决新任务

经过 SFT 和 RL，得到 Frontis-MA1。

测试或实际解题时，Frontis-MA1 一般被冻结，不再使用 slime 更新参数。

此时由 OpenMLE-Evo 管理搜索过程：

```text
新任务
  │
  ├── 调用 Frontis-MA1 生成多个 Draft
  │
  ├── sandbox 执行所有 Draft
  │
  ├── 选择有希望的程序继续 Improve
  │
  ├── 对失败程序调用 Debug
  │
  ├── 对互补分支调用 Crossover
  │
  ├── 持续保存新程序和执行结果
  │
  └── 预算耗尽后选择最好的合法程序
```

这里不断变化的是候选程序：

```text
程序 v1 -> 程序 v2 -> 程序 v3 -> 更好的程序
```

不是下面这种模型自我训练：

```text
Frontis-MA1
-> 自己调用 slime
-> Frontis-MA2
-> 再调用 slime
-> Frontis-MA3
```

论文没有完成后一种过程。

## 10. OpenMLE-Evo 在测试时为什么还需要“经验”

随着搜索持续进行，程序会越来越多。如果搜索器只看当前分数最高的程序，会出现两个问题。

### 问题一：过早只搜索一条路线

假设当前有两个程序：

```text
程序 A：当前分数最高，但连续几次 Improve 都没有进步
程序 B：当前略低，但刚刚比自己的 parent 提升很多，而且采用了新方法
```

如果永远选择 A，搜索可能卡在局部最优。OpenMLE-Evo 会同时考虑：

- 当前质量；
- 相对父程序的进步；
- 方法是否新颖、是否还没被充分探索。

所以 B 仍有机会获得下一次 Improve。

### 问题二：完整历史越来越长

如果每次都把几十个程序、日志和分析全部放进 prompt：

- token 会越来越长；
- 旧信息会干扰当前操作；
- Debug 看到大量无关的成功方案；
- Crossover 很难分清两个分支各自真正的优点。

因此 OpenMLE-Evo 保存两种信息。

#### 节点卡片

每个程序有一张简短记录：

```text
它由哪个操作产生
父程序是谁
能否运行
分数和错误
运行时间
采用了哪类方法
相对父程序有没有进步
```

#### 全局任务看板

汇总当前任务整体状态：

```text
目前最好的程序
已经尝试过哪些方法
哪些方向很少探索
哪些错误反复出现
最近是否还有进步
所有程序之间的父子关系
```

只有当某个节点真的被选中时，系统才整理与当前操作有关的少量历史，而不是把整棵树全部塞进 prompt。

### 不同操作看到不同经验

#### Draft

不继承旧节点记忆，尽量开一条独立的新路线。

#### Improve

主要看：

- 当前父程序；
- 它最近几代 ancestors；
- 从同一个父节点产生的几个 sibling；
- 哪些修改曾经有帮助或有害。

#### Debug

主要看：

- 当前失败程序；
- 当前 traceback；
- 以前出现相同错误时如何处理。

#### Crossover

主要看：

- 两个父程序各自的路线；
- 每条路线的强项和弱点；
- 哪些方法互补；
- 哪些组合可能冲突。

这种设计的核心不是“让模型记住所有历史”，而是：

> 针对下一步要做的事情，只提供少量直接有用的证据。

## 11. 四个模块分别做什么

现在可以重新理解最初提到的四个部分。

### 11.1 OpenMLE-Gym：自动运行和验收代码

它负责：

- 把不同来源的数据集整理成标准任务；
- 隔离公开数据和隐藏答案；
- 在 Docker sandbox 中运行候选程序；
- 限制 CPU、GPU 和运行时间；
- 检查 submission；
- 返回分数、错误、日志和运行时间。

它不训练 Frontis-MA1，也不决定搜索方向。

一句话：

> Gym 是可以自动出题、运行程序和打分的实验环境。

### 11.2 OpenMLE-ERL：把执行结果变成模型训练信号

它包括两个部分：

1. 从 teacher 搜索轨迹中筛选 Draft、Improve、Debug、Crossover 数据，进行 SFT。
2. 让当前模型在线生成程序，用 sandbox 分数作为 reward，进行 RL。

它还负责处理：

- 不同任务指标方向不一致；
- 大量程序运行失败；
- 候选程序耗时差异巨大；
- 训练时怎样选择合适的父程序；
- 怎样避免只学会生成“勉强合法”的程序。

一句话：

> ERL 是教大语言模型怎样根据真实执行反馈写出更好下一版程序的方法。

### 11.3 OpenMLE-Evo：测试时管理长期搜索

它是一个预定义的搜索器，负责：

- 维护候选程序和父子关系；
- 决定下一步使用哪个操作；
- 选择要继续修改的程序；
- 选择 Crossover 的两个父程序；
- 保存每次实验的结果；
- 找出与当前操作有关的少量经验；
- 在预算结束时选择最终程序。

它不更新 Frontis-MA1 参数。

一句话：

> Evo 是负责组织多轮尝试的项目经理。

### 11.4 Frontis-MA1：真正生成代码的模型

Frontis-MA1 是基础 Qwen 模型经过前述 SFT 和 RL 后得到的语言模型。

它根据不同输入完成四种工作：

```text
Draft：根据任务从零写一份程序
Improve：根据父程序和反馈写更好的版本
Debug：根据失败程序和错误进行修复
Crossover：根据两个父程序生成融合方案
```

它既是 OpenMLE-ERL 的训练结果，也是 OpenMLE-Evo 在搜索时反复调用的代码生成器。

一句话：

> Frontis-MA1 是被训练得更会写、改、修和组合机器学习程序的程序员。

## 12. “自进化”到底体现在哪里

论文里存在两个层次的进化。

### 第一层：一个任务内部的候选程序进化

```text
旧程序
-> Improve / Debug / Crossover
-> 新程序
-> sandbox 验证
-> 保留好的分支
-> 继续产生下一代程序
```

这里进化的是 Python 程序，不是 Frontis-MA1 的模型参数。

### 第二层：用程序进化经验训练“负责改程序的模型”

```text
大量程序搜索树
-> 找出成功的修改过程
-> 做成 SFT 和 RL 信号
-> 使用 slime 更新基础语言模型
-> 得到更强的 Frontis-MA1
```

这里被改进的是负责产生程序变体的大语言模型。因此论文称它为 meta-evolution：不仅进化候选程序，还用进化经验训练“产生变体的模型”。

但这还不是完整的递归自我改进。

论文没有展示：

- Frontis-MA1 自己修改 slime；
- Frontis-MA1 自己设计下一代训练算法；
- Frontis-MA1 自己训练 Frontis-MA2；
- Frontis-MA2 再自主训练 Frontis-MA3；
- 搜索器自己改进自己的搜索规则。

更准确的说法是：

> 论文实现了“搜索经验反过来训练搜索中使用的代码生成模型”，这是走向递归自我改进的一步，而不是已经实现完整 RSI。

## 13. 最容易混淆的几个问题

### 13.1 是不是给一个任务，让模型使用 slime 训练新模型

不是。

slime 由论文作者使用，用于集中训练 Frontis-MA1。模型解具体任务时不会自己调用 slime。

### 13.2 是不是先把所有程序生成完，再统一训练

SFT 基本是这种方式：

```text
先采集和执行大量程序
-> 过滤并保存数据
-> 再集中做 SFT
```

RL 则是交替进行：

```text
当前模型 rollout
-> sandbox reward
-> 更新模型
-> 新模型继续 rollout
```

### 13.3 搜索树是不是神经网络的一部分

不是。搜索树是外部程序维护的数据结构。

节点是一份候选 Python 程序，边表示 Draft、Improve、Debug 或 Crossover 产生关系。

### 13.4 为什么不能只保留每个任务的最好程序

因为最好程序只能教模型“答案是什么”，无法教模型：

- 怎样从较差程序走到较好程序；
- 怎样修复具体错误；
- 哪个局部修改带来了收益；
- 怎样融合两个不同方案。

搜索树保存了这些中间过程。

### 13.5 训练时和测试时都有搜索树吗

都有，但用途不同。

- 训练数据采集时：搜索树主要用来制造和筛选程序修改样本。
- RL 时：程序数据库提供 Improve、Debug、Crossover 所需的父程序状态。
- 测试时：搜索树用于在固定预算内长期探索，最终找到最好的候选程序。

### 13.6 测试时模型参数会不会继续更新

标准 OpenMLE-Evo 搜索中不会。测试时变化的是候选程序、搜索树、节点选择和经验内容，不是 Frontis-MA1 参数。

## 15. 核心结论

理解这篇论文只需要抓住以下五点：

1. **Frontis-MA1 不会自己调用 slime 训练自己。**
2. **搜索器是人写好的外部程序，模型只负责生成新代码。**
3. **搜索树保存候选程序的父子关系，用来制造 Improve、Debug 和 Crossover 训练数据。**
4. **SFT 是先离线采集数据再训练；RL 是 rollout、sandbox 执行和参数更新交替进行。**
5. **论文中的进化首先是候选程序进化，然后用这些进化经验训练代码生成模型；它还不是完整的递归自我改进。**

## 16. 从四个层级看：论文到底实现了哪种“自进化”

如果把一个完整的自进化系统分层，只分成“模型、Harness、Evaluator”三层还不够，因为这篇论文最直接进化的对象其实是候选 Python 程序。更准确的划分是四层：

| 层级 | 发生变化的对象 | 论文是否实现自动进化 |
|---|---|---|
| 0. Solution | 当前任务的 Python 代码和代码内部训练的任务模型 | 是，这是 OpenMLE-Evo 最主要的工作 |
| 1. Model | 负责生成代码的语言模型权重 | 部分实现，通过程序进化经验进行 SFT 和 RL |
| 2. Harness | 搜索算法、选节点规则和 memory 机制 | 没有自进化，算法由人设计并固定 |
| 3. Evaluator | 任务指标、reward 目标和评价标准 | 没有自进化，基本由任务预先确定 |

### 16.1 Solution 层：实现得最完整

OpenMLE-Evo 在一个新任务上反复执行：

```text
Python 程序 A
-> Improve / Debug / Crossover
-> Python 程序 B
-> sandbox 执行和评价
-> 保留有价值的分支
-> Python 程序 C
```

测试阶段不断变化的是候选 Python 程序，以及程序内部训练出的 LightGBM、神经网络等任务模型。Frontis-MA1 本身通常保持冻结。

因此，论文最直接实现的是：

> 在固定搜索规则和固定 evaluator 下，根据执行反馈进化当前任务的 solution。

### 16.2 Model 层：实现了一次受控的 meta-evolution

程序搜索产生的经验会被用于训练代码生成模型：

```text
大量程序进化轨迹
-> 筛选有效的 Draft / Improve / Debug / Crossover
-> SFT + RL
-> 更新基础 Qwen 权重
-> 得到 Frontis-MA1
```

“负责改进程序的模型”本身被程序进化经验改进了，所以论文称其为 meta-evolution。

但这个过程仍由研究人员搭建和启动：研究人员准备任务、设计搜索器、收集数据、配置 slime 并执行训练。论文没有展示下面这种持续、自主的模型迭代：

```text
Frontis-MA1
-> 自主收集下一代训练数据
-> 自主修改训练方法并调用 slime
-> 训练 Frontis-MA2
-> Frontis-MA2 再自主训练 Frontis-MA3
```

所以 Model 层是“部分实现”，不是多代递归的模型自进化。

### 16.3 Harness 层：运行状态会变化，算法本身不会进化

OpenMLE-Evo 在搜索过程中会根据新经验改变下一步行为：

```text
新节点加入搜索图
-> 节点选择概率发生变化
-> 提供给 operator 的 memory 发生变化
-> 下一步可能选择不同 parent
```

但是，发生变化的是 Harness 的运行状态，不是 Harness 自己的算法。下面这些内容仍由人预先设计：

- 使用 Draft、Improve、Debug、Crossover 四种操作；
- 根据当前质量、相对进步和方法新颖度选择节点；
- 三类信号的权重；
- 如何选择 ancestors 和 siblings；
- memory 保存哪些字段；
- 何时做 Crossover；
- 如何分配搜索预算。

因此它属于：

```text
固定搜索算法根据不断变化的状态做自适应决策
```

而不是：

```text
搜索算法根据经验修改自己的代码、规则或参数
```

论文也把“让 evolutionary system 自身成为进化对象”列为未来工作。

### 16.4 Evaluator 层：评价标准没有自进化

每个任务使用预先确定的 evaluator，例如 accuracy、RMSE、log loss 或 AUC。隐藏答案和 `metric.py` 在任务构建时已经固定。

RL 训练中虽然会根据当前模型能够达到的分数范围动态调整 reward 的映射尺度，但这只是为了让不同候选的差异更容易被训练算法识别，并不表示 evaluator 学会了新的评价标准。

Evaluator 仍然主要回答：

```text
程序能否运行？
submission 是否合法？
最终任务指标是多少？
```

它不能充分判断：

- 一个研究方向是否值得继续；
- 方法是否具有迁移价值；
- 推理和实验设计是否高质量；
- 暂时失败的实验是否包含有价值的发现；
- 当前评价目标本身是否需要修改。

所以 Evaluator 层没有实现自进化。

### 16.5 最准确的结论

```text
候选 Solution：实现了进化
Model 权重：实现了一次由人组织的 meta-evolution
Harness 自身：没有进化
Evaluator 自身：没有进化
```

因此，如果只考虑 Model、Harness、Evaluator 三个元层级，可以说论文只部分触及了第一层，其余两层虽然由作者进行了人工设计和增强，但没有通过运行经验自动改进自身。

如果把候选程序也算进去，则论文最完整的贡献其实位于 Solution 层：它先让 Python 程序在执行反馈下进化，再用这些进化经验训练负责产生程序变体的语言模型。
